# 代码学习规范

在本项目中编写、修改或重构代码时，遵循以下规则。

## 注释与可读性

- 为新增或修改的代码添加中文注释，帮助用户理解代码的职责、实现思路和关键语法。
- 对模块、结构体、枚举、重要字段、公开函数、复杂分支、状态变化和不直观的 API 调用提供详细说明。
- 解释“为什么这样实现”以及关键取舍，不要只把代码逐字翻译成注释。
- 简单赋值、显而易见的控制流或已有清晰命名无需机械重复注释；保持注释准确，并随代码同步更新。
- 示例代码同样应包含足够的教学说明。

## 功能模块拆分

- 尽量让一个功能对应一个独立文件；功能包含多个紧密协作的模块时，为其建立独立目录。
- 入口文件只负责模块声明、组装、路由或启动，避免堆积具体业务实现。
- 将功能自己的实现、类型、测试及资源放在该功能文件或目录附近，降低跨功能耦合。
- 小型辅助类型或只服务于单个功能的少量代码可以保留在同一文件中；不要为了形式上的拆分创建没有独立职责的文件。
- 添加功能前先检查现有目录结构，优先延续项目已有的组织方式。

## README 开发文档

- 每次引入或变更开发流程后，检查项目根目录的 `README.md`，确保实际可执行的命令完整且与代码同步。
- 文档至少覆盖：环境准备、所有依赖项的安装或获取、编译检查、开发构建、发布构建/打包、运行、启动、测试和调试。
- 对每条命令说明用途、运行目录和必要前置条件；区分开发构建与发布构建产物。
- 新增、删除或调整依赖时，同步更新依赖列表、用途和安装步骤。由包管理器统一获取的依赖，要写明清单文件及获取命令。
- 不要记录未经验证或与当前项目技术栈无关的命令。可执行时，实际运行关键命令进行验证；无法验证时明确标注原因。

## 错误处理

- 使用 `thiserror` 定义项目错误类型，不使用 `anyhow` 编写新的错误处理代码。
- 为不同失败原因定义语义明确的错误枚举或结构体，避免只返回缺少上下文的字符串。
- 使用 `#[from]` 或 `#[source]` 保留底层错误链；错误信息应说明失败的操作，但不得泄露敏感数据。
- 修改仍在使用 `anyhow` 的相关代码时，在不扩大任务范围的前提下将其迁移到 `thiserror`；不要为了迁移而改动无关模块。
- 添加 `thiserror`、移除 `anyhow` 或调整错误处理方式时，同步更新 `Cargo.toml`、锁文件和 `README.md` 的依赖说明。
- `thiserror` 通常通过派生宏实现 `std::error::Error`。首次引入或新增其宏用法前，仍需遵循下方“宏的使用”规则，先解释使用原因和收益。

## 诊断日志

- 为问题排查所需的关键路径添加日志，包括应用启动和关闭、重要状态变化、用户触发的关键操作、外部资源访问、耗时操作结果以及错误发生的位置和上下文。
- 日志应帮助回答“执行到了哪里、使用了哪些非敏感条件、结果是什么、为什么失败”，不要只输出含义不明的固定文本。
- 合理选择日志级别：`error` 记录导致操作失败的问题，`warn` 记录可恢复的异常，`info` 记录重要生命周期和业务事件，`debug` 或 `trace` 记录开发排查细节。
- 避免在高频循环、渲染循环或频繁回调中无条件输出日志；必要时降低日志级别、采样或只记录状态变化，防止日志噪声和性能问题。
- 不得记录密码、令牌、密钥、完整用户输入、图片 Base64、个人信息或其他敏感数据。需要定位数据时，仅记录安全的长度、类型、数量、脱敏标识或摘要。
- 错误日志应保留错误链和必要上下文，但避免同一错误在多个调用层重复记录。通常在能够决定如何处理错误的边界处记录一次。
- 优先沿用项目已有日志框架；项目尚无日志能力时，选择适合当前技术栈的结构化日志方案，并同步更新依赖、初始化代码和 `README.md` 中的日志级别及查看方式。
- 若日志 API 通过宏调用，首次引入前仍需遵循“宏的使用”规则，说明选择该宏的原因、收益和调试影响。

## 宏的使用

- 引入新的宏或扩大现有宏的用途前，先向用户说明，再继续实现。
- 说明必须包括：为什么需要宏、它相较普通函数或类型方案的好处、它解决的具体问题，以及主要可读性或调试成本。
- 优先考虑普通函数、泛型、trait 或明确的数据结构。只有宏能显著减少重复、需要编译期生成，或能表达普通语言结构难以表达的模式时才使用宏。
- 代码中对非显而易见的宏调用添加注释；在 `README.md` 或相关开发文档中记录影响项目构建或使用方式的重要宏。

## 完成前检查

- 确认新增代码具有准确、面向学习的注释。
- 确认功能边界与文件或目录边界基本一致。
- 确认新增错误类型使用 `thiserror`，并且没有新增 `anyhow` 用法。
- 确认关键执行路径具备足够的诊断日志，同时没有敏感信息、重复日志或高频日志噪声。
- 确认 `README.md` 覆盖本次变更涉及的依赖与全部开发命令。
- 确认所有新宏均已事先解释，并记录其必要性和收益。
- 代码/等宽文本输出区域使用 JetBrains Mono 字体，新增等宽文本区域时不要使用其他字体。
