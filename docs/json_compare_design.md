# JSON 比较工具设计文档

本文记录 JSON 比较工具的设计思路、核心算法和关键决策。文档以当前代码为准：
比较引擎在 `src/tools/json_diff.rs`，UI 层在 `src/tools/json_compare.rs`，公共工具在 `src/tools/json_utils.rs`。

## 1. 要解决的问题

比较两个 JSON 文档，直观地告诉用户：**哪些字段新增了、哪些删除了、哪些值被修改了**。

这类工具的常见做法是做**文本 diff**（像 `diff` 命令那样逐行比对），但对 JSON 效果很差：

```json
// 左侧                          // 右侧
{"a": 1, "b": 2}                 {"b": 2, "a": 1}
```

这两个 JSON 语义上完全相同，但文本 diff 会报告"整段都变了"。缩进、换行、键顺序的任何变化都会产生大量无意义的差异（假阳性）。

## 2. 核心设计决策：结构化对齐，而非文本 diff

本工具不做文本比较，而是先把 JSON 解析成树（`serde_json::Value`），再按树的结构对齐比较。三条对齐规则：

| 规则 | 说明 | 例子 |
|------|------|------|
| 对象按 Key 对齐 | 两侧相同的 Key 视为同一字段 | `{"a":1,"b":2}` vs `{"b":2,"a":1}` → 无差异 |
| 数组按下标对齐 | 按索引位置一一对应 | `[1,2]` vs `[2,1]` → 两个位置都是"修改" |
| 缺失侧留空行 | 一侧没有的字段，对应位置显示空行 | 保证两侧行号始终一一对应 |

### 为什么数组按下标而不是按内容匹配？

`[1,2]` vs `[2,1]` 按内容匹配会报"删除 1、新增 1"，按下标则报"位置 0 从 1 改成 2"。后者更简单、结果可预测，也符合"数组顺序有意义"的直觉。按内容匹配（LCS 之类的算法）在元素重复时结果不稳定，刻意不做。

### 为什么先排序 Key？

解析后立即用 `json_utils::sort_keys` 递归排序所有对象的 Key。这样比较结果不受键顺序影响，稳定可预测。注意 `sort_keys` 只排对象、不动数组（数组顺序是有意义的）。

原始（未排序）的格式化文本也单独保存在 `raw_left` / `raw_right` 中，供"展开原始 JSON"功能使用。

## 3. 数据结构

```rust
// 一行的变化类型
enum ChangeKind { Equal, Added, Removed, Modified }

// 差异行：左右两侧的文本总是成对出现
struct DiffRow {
    left: String,       // 空串 = 该行在左侧不存在
    right: String,      // 空串 = 该行在右侧不存在
    kind: ChangeKind,
}

struct Comparison {
    rows: Vec<DiffRow>,   // 对齐后的全部行
    raw_left: String,     // 原始左侧文本（未排序 Key）
    raw_right: String,
}
```

`DiffRow` 的关键性质：**`rows` 中第 i 行的 `left` 和 `right` 在界面上显示在同一行号**。这是"缺失侧留空行"规则的目的——左右两个编辑器并排显示时，滚动到任意位置都能看到对应的两侧内容。

`kind` 的含义是"从左侧看右侧"：`Added` = 右侧有左侧无（绿色），`Removed` = 左侧有右侧无（红色），`Modified` = 两侧都有但值不同（黄色）。

## 4. 对齐算法

入口是 `align(left, right, depth, key, commas, rows)`，按值类型分三种情况：

### 4.1 两侧都是对象

1. 输出一对待号行 `{` / `{`
2. 取两侧 Key 的**并集**（`BTreeSet`，自动按字母序）
3. 对每个 Key 递归对齐两侧的对应值；某侧没有该 Key 就传 `None`
4. 输出一对闭括号行 `}` / `}`

### 4.2 两侧都是数组

1. 输出 `[` / `[`
2. 按下标 `0..max(len_a, len_b)` 逐位递归对齐；较短数组超出的位置传 `None`
3. 输出 `]` / `]`

### 4.3 其他情况（叶子值、或容器类型不匹配）

- 一侧是 `None` → `Added` / `Removed`
- 两侧值相等 → `Equal`
- 两侧值不等（包括类型不同，如 `1` vs `"1"`、`{}` vs `[]`）→ `Modified`

如果值本身是多行的（比如一侧是空对象、另一侧是多行对象，走不到对象分支时），用 `block()` 展开成多行文本，两侧补齐到相同行数。

### 4.4 尾逗号：保证每侧都是合法 JSON

每行末尾是否带逗号，左右两侧**独立计算**：

```
左侧 {"a":1,"b":2}     右侧 {"a":1}
                       
  "a": 1,                "a": 1      ← 左侧 a 后面还有 b，要逗号；右侧 a 是最后一个，不要
  "b": 2                            ← 右侧空行
```

所以 `align` 的参数 `commas: (bool, bool)` 记录"本行在左侧/右侧后面是否还有兄弟节点"。这样从 `rows` 拼出的 `text(true)` / `text(false)` 各自都是可重新解析的合法 JSON——有测试专门保证这一点（`missing_keys_get_blank_lines_and_sides_remain_json`）。

## 5. 为什么用显式栈 + 迭代，而不是递归或尾递归

`align` 最初是自然递归写法，后来改为显式栈 + 迭代。原因：

**尾递归为什么不行（两点缺一不可）：**

1. **Rust 不保证尾调用优化**。即使写成尾递归，编译器（尤其 debug 模式）不保证消除栈帧，深递归照样爆栈。
2. **`align` 结构上就不是尾递归**。对象分支在 `for` 循环里对每个 Key 递归（多个递归调用点），且递归返回后还要输出闭括号行（递归之后仍有工作）。"先序遍历 + 收尾工作"的结构没有尾递归形式。

**迭代做法**：定义任务枚举，把调用栈搬到堆上（`Vec<AlignTask>`）：

```rust
enum AlignTask<'a> {
    Visit { left, right, depth, key, commas },  // 对齐一对值（= 原递归入口）
    Close { depth, bracket, commas },           // 输出闭括号（= 原递归的收尾工作）
}
```

- 遇到容器：先输出开括号 → 把 `Close` 任务入栈 → 把子任务**逆序**入栈
- 栈是后进先出，所以 `Close` 先入栈（后执行）、子任务逆序入栈（弹出即正序）——弹出顺序与递归版完全一致
- 栈深度只受内存限制，不受调用栈大小限制

**一个容易忽略的顺序细节**：子任务必须逆序入栈。对象有 a、b、c 三个 Key 时按 c、b、a 入栈，弹出时才是 a、b、c。代码中的 `.rev()` 就是干这个的。

**实际触达概率**：`serde_json` 默认解析深度限制约 128 层，超限会在 `parse` 阶段先报错，所以正常情况下轮不到 `align` 爆栈。这次改动的意义是防御性的——换解析器（如 json5 路径）或放宽限制时，`align` 不会成为新瓶颈。

## 6. UI 层设计

### 6.1 比较流程（`JsonCompareTool::compare`）

```
点击「比较」
  → 读两侧编辑器文本，分别 parse
  → 失败：在对应侧显示错误 Alert，不动编辑器内容
  → 成功：Comparison::new(a, b)
       → 保存原始输入到 original_left/right（供"返回编辑"恢复）
       → 编辑器内容替换为对齐后的 text(true)/text(false)
       → decorate() 添加差异高亮
       → 编辑器变只读
```

**为什么比较后编辑器只读？** 差异高亮（`TextDecoration`）是按**字节偏移**定位的。如果用户编辑了对齐后的文本，偏移就失效了，高亮会错位。所以比较模式下锁定编辑，要改就先"返回编辑"恢复原始输入。

### 6.2 差异高亮（`decorate`）

遍历 `rows`，跳过 `Equal` 行，其余按 `kind` 着色（绿/红/黄，透明度 0.2 的背景色）。装饰位置通过累加每行文本长度（含换行符）算出字节偏移区间。

**性能优化**：连续相同 `kind` 的行合并为一个 `TextDecoration`（原来每行一个装饰）。差异行成片出现是常态，合并后装饰数量从"行数"降为"差异块数"，显著减少编辑器的装饰管理开销。

主题切换时通过 `observe_global::<Theme>` 重新执行 `decorate`，保证高亮颜色跟随主题。

### 6.3 滚动同步（最容易踩坑的部分）

两个编辑器并排，要求滚动一侧时另一侧跟随，保持对齐行在同一垂直位置。实现是 `cx.observe` 监听两侧编辑器变化，触发 `sync_scroll`。

**这里有一个 GPUI 框架级别的坑**：`EditorState::set_scroll_offset` 只是设置 `deferred_scroll_offset` 并立即 `notify()`，真正生效要等下一帧布局；而 `scroll_offset()` 读的是当前实际值（旧值）。没有防护时的死循环：

```
左滚动 → observe 触发 → 设置右侧 deferred → 右侧 notify
  → observe 又触发 → 读到右侧"旧值"（deferred 还没生效）
  → 又设置左侧 deferred → 左侧 notify → …… 无限循环，界面卡死
```

**防护手段**（三重，见 `sync_scroll` 实现与注释）：

1. `syncing_scroll: Cell<bool>` 重入标志：同步期间直接返回，阻断同一帧内的循环
2. `cx.defer(...)` 在 effect 循环结束后重置标志，保证下一次真实滚动仍可触发同步
3. 值相同（`abs() < 0.01px`）直接返回：deferred 生效后两侧值相等，observe 回调到此为止

浮点比较用 0.01px 的 epsilon，是因为滚动值经行高对齐、钳制后可能存在微小浮点误差，`!=` 比较不可靠。

## 7. 模块职责划分

| 模块 | 职责 | 关键导出 |
|------|------|----------|
| `json_diff.rs` | 纯比较引擎，无 UI 依赖 | `Comparison`、`DiffRow`、`ChangeKind` |
| `json_compare.rs` | UI 层：编辑器、高亮、滚动同步、交互 | `JsonCompareTool` |
| `json_utils.rs` | 解析（严格 JSON / JSON5）、Key 排序 | `parse`、`sort_keys` |

比较引擎与 UI 完全分离：`json_diff.rs` 不依赖 GPUI，可独立测试。测试覆盖：缺失 Key 的空行与合法性、键序无关/数组保序、空容器与类型变化、100 层深嵌套不溢出、数组元素为对象的混合嵌套。

## 8. 已知的设计取舍

- **数组不做内容匹配**：`[1,2]` vs `[2,1]` 报"修改"而非"删除+新增"。简单可预测，但不适合"数组是无序集合"的场景。
- **Modified 是整行级别**：一个值从 `1` 改成 `2`，整行标黄，不做行内字符级高亮。
- **比较后只读**：换取装饰定位的正确性，代价是多一步"返回编辑"。
